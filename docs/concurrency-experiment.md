# 재생 완료 + 스킵 동시 요청 실험

> 한 줄 요약: 현재 코드는 "재생 완료"와 "스킵"이 겹치면 곡이 2개 이상 넘어가거나 PLAYING이 여러 곡이 된다.
> 조건부 UPDATE와 비관적 락 둘 다 정합성은 100% 지켰지만, 동시 요청이 많을수록 조건부 UPDATE가 2~3배 빨랐다.
> 최종 선택은 **조건부 UPDATE(멱등 전환)**.

- 브랜치: `experiment/concurrency`
- 실험 코드: `src/test/java/com/gokchu/gokchu/queue/experiment/`
- 실행: `./gradlew concurrencyExperiment` (Docker 필요, 약 3분. 원본 결과는 `build/reports/concurrency-experiment.md`)

---

## 1. 문제 상황

TV 플레이어는 곡이 끝나면(`ENDED`) `POST /now-playing/complete`를 보내고, 관리자는 같은 곡을
`POST /queue-items/{id}/skip`으로 넘길 수 있다. 곡이 끝나기 직전에 관리자가 스킵을 누르면 두 요청이
거의 동시에 서버에 도착한다. 두 요청의 의도는 같다: **"곡 A를 끝내고 다음 곡 B를 틀어라"**. 그러니
결과도 곡 1개만 넘어가야 한다.

### 현재 코드가 now-playing을 바꾸는 방식 (`QueueService`)

| 요청 | 동작 |
|---|---|
| `completeNowPlaying(tableToken)` | **곡 ID를 받지 않는다.** PLAYING인 곡을 조회 → `finish()`(DONE) → 가장 오래된 WAITING을 `play()` |
| `skip(tableToken, id)` | 지정한 곡 조회 → DONE/SKIPPED면 409 → `skip()` → 재생중이었으면 다음 WAITING을 `play()` |

두 메서드 모두 **읽고(SELECT) → 자바 코드에서 판단하고 → 엔티티 필드를 바꾼 뒤 → 커밋 시점에
dirty checking이 `UPDATE ... WHERE id=?`를 날리는** 구조다. 판단과 쓰기가 원자적이지 않다(check-then-act).
`version` 컬럼이 없어서 낙관적 락도 동작하지 않는다.

### 코드만 보고 내린 판단: 동시 요청에 안전하지 않다

1. **complete가 멱등하지 않다.** 요청의 의미가 "A가 끝났다"가 아니라 "지금 곡이 끝났다"다.
   스킵이 먼저 처리돼 B가 올라온 뒤 complete가 도착하면, 방금 시작한 B까지 끝내버린다.
   이건 동시성이 없어도, 요청이 순서대로 하나씩 처리돼도 생긴다.
2. **check-then-act 경쟁.** 두 트랜잭션이 둘 다 "A가 PLAYING"이라고 읽으면 둘 다 통과해서 각자
   다음 곡을 올린다.

## 2. 실험 환경

| 항목 | 값 |
|---|---|
| DB | PostgreSQL 16.15 (Testcontainers, `postgres:16-alpine`, 운영 docker-compose와 같은 이미지) |
| 격리 수준 | READ COMMITTED (PostgreSQL 기본값, 앱에서 바꾸지 않음) |
| 스키마 | Flyway V1~V4 그대로 (실험 때문에 바꾼 스키마 없음) |
| 커넥션 풀 | HikariCP 기본값 `maximumPoolSize=10` |
| YouTube | `@MockitoBean`으로 `YoutubeApiClient`를 막음. 큐 데이터는 JDBC로 직접 넣어서 영상 검증 경로를 타지 않음 |
| 머신 | 로컬 Windows 11 + Docker Desktop (절대 시간은 참고용이고, 방식 간 상대 비교만 의미 있음) |

**왜 Testcontainers인가**: 원래 `GokchuApplicationTests`가 로컬 Postgres가 없어서 안 돌았다.
docker-compose는 사람이 먼저 띄워둬야 하고, 이 머신은 5432 포트를 네이티브 Postgres가 쓰고 있어서
설정이 꼬인 이력도 있다. Testcontainers는 테스트가 빈 DB를 직접 띄우고 내리므로 누가 돌려도 같은
조건이 된다. `@ServiceConnection`이 datasource 설정을 자동으로 주입한다. 이 변경으로
`GokchuApplicationTests`도 처음 통과했다.

### 측정 방법

한 번의 시행(trial)은 다음 순서로 진행했다.

1. 큐 초기화: 곡0(A, PLAYING), 그 뒤로 대기곡 N+5개. `requested_at`이 겹치지 않게 1초씩 차이를 뒀다.
2. 스레드 N개 중 절반은 `complete(A)`, 절반은 `skip(A)`를 실행한다.
3. `CountDownLatch` 3개를 쓴다.
   - `ready`: 모든 스레드가 출발선에 설 때까지 기다린다.
   - `start`: 한꺼번에 출발시킨다.
   - `done`: 모두 끝날 때까지 기다린다.
4. 시간은 `start` 직후부터 `done`까지 잰다. 스레드 생성 비용이 섞이지 않게 하기 위해서다.
5. 끝난 뒤 DB 상태를 확인한다.
   - DONE+SKIPPED 개수 = 넘어간 곡 수
   - PLAYING 개수
   - **정상**: 넘어간 곡이 1개이고 PLAYING이 B 하나뿐인 경우

시행 횟수는 (방식, N) 조합마다 워밍업 5회를 빼고 100회다. 같은 실험을 두 번 돌렸고, 정합성 수치는
같았으며 시간 순위도 같았다. 아래 표는 두 번째 실행 결과다.

추가해서는 이 문제를 막을 수 없다. 락은 요청을 한 줄로 세울 뿐이고, 줄을 선 뒤에도 complete는

### 3-2. 동시 실행: complete 1개 + skip 1개 (N=2)

| | 2곡 이상 넘어감 | PLAYING 중복 | 정상 |
|---|---|---|---|
| 현재 코드 | 0 / 100 | **100 / 100** | 0 / 100 |

"곡 2개가 넘어가는" 모양으로는 깨지지 않았다. 대신 **매번 B와 C가 동시에 PLAYING이 됐다.**
TV는 둘 중 먼저 신청된 B를 틀지만, C는 PLAYING 상태로 남는다. 그래서 다음 완료 때 큐 순서가
틀어진다. 100번 중 100번 같은 결과가 나온 원인은 5장에서 설명한다.

## 5. CS 관점 원인 설명

### 5-1. 현재 코드: N=2에서 매번 PLAYING이 2곡이 되는 이유

우연한 타이밍 문제가 아니라, Hibernate와 PostgreSQL 동작이 만들어내는 **결정적인** 순서다.

```
T1 complete                                  T2 skip(A)
SELECT PLAYING -> A                          SELECT A -> PLAYING (아직 아무도 안 바꿈)
A.finish()                                   A.skip()
SELECT 첫 WAITING  -- 직전 auto-flush:         SELECT 첫 WAITING  -- 직전 auto-flush:
  UPDATE A=DONE (A 행 락 획득)                  UPDATE A=SKIPPED -> A 행 락 대기 ...
  -> B
B.play()
COMMIT (UPDATE B=PLAYING, 락 해제)  ------>   락 획득, A를 SKIPPED로 덮어씀 (lost update)
                                             SELECT 첫 WAITING -> 새 스냅샷: B는 이미 PLAYING -> C
                                             C.play(), COMMIT
결과: A=SKIPPED, B=PLAYING, C=PLAYING
```

- **auto-flush**: Hibernate는 JPQL 쿼리를 실행하기 직전에, 그 쿼리 결과에 영향을 줄 수 있는 변경을
  먼저 DB에 보낸다(FlushMode.AUTO). 그래서 "다음 곡 조회" 직전에 `UPDATE A`가 먼저 나간다.
- **행 락**: PostgreSQL에서 UPDATE는 그 행에 쓰기 락을 걸고 커밋 때까지 유지한다. 그래서 T2는
  자기 `UPDATE A`에서 T1이 커밋할 때까지 멈춘다.
- **READ COMMITTED는 문장마다 새 스냅샷을 쓴다.** 락이 풀린 뒤 T2가 실행하는 "첫 WAITING 조회"는
  T1의 커밋이 반영된 새 스냅샷을 본다. B는 이미 PLAYING이니 C를 고른다. 그런데 T2가 "A가 PLAYING이니
  내가 다음 곡을 올려야 한다"고 판단한 근거는 락을 기다리기 **전**의 낡은 스냅샷이었다.
- 즉 **쓰기는 DB 락 덕분에 한 줄로 섰지만, 쓰기를 할지 말지 정한 판단(check)은 줄을 서기 전에
  끝나 있었다.** 이게 TOCTOU(time-of-check to time-of-use) 문제다. 또 Hibernate는 바뀐 컬럼을
  `WHERE id=?`만으로 덮어쓰므로, T1이 쓴 DONE이 T2의 SKIPPED에 덮였다(lost update).

N=10에서 "최대 동시 PLAYING 10"이 나온 이유도 같다. 요청 10개(커넥션 풀 크기와 같음)가 전부 "A가
PLAYING"이라는 판단을 먼저 내렸다. 그 뒤 A 행 락에서 한 줄로 서서 각자 다음 곡을 하나씩 올렸다.
N=100, 500에서는 풀(10개)보다 요청이 많다. 그래서 늦게 커넥션을 받은 complete들은 그 시점의
"지금 곡"(B, C, ...)을 끝내버렸고, 곡이 15~67개까지 넘어갔다(3-1의 멱등성 문제).

### 5-2. 해결책 ① 조건부 UPDATE: 판단과 쓰기를 한 문장으로

```sql
UPDATE queue_items SET status = 'DONE' WHERE id = :A AND status = 'PLAYING'
-- 반환값(바뀐 행 수)이 1인 트랜잭션만 다음 곡을 올린다. 0이면 아무것도 안 한다.
```

- "A가 아직 PLAYING인가"라는 확인이 WHERE 절 안에 들어가 있다. 그래서 확인과 변경 사이에 끼어들
  틈이 없다(compare-and-set).
- PostgreSQL READ COMMITTED에서 UPDATE가 다른 트랜잭션의 행 락을 기다렸다가 풀리면, **그 행의 최신
  커밋 버전으로 WHERE를 다시 평가한다**(EvalPlanQual). 늦게 온 요청은 "A는 이미 DONE"을 보고
  0행이 된다.
- 0행이 된 요청은 락을 잡지 않고 바로 지나간다. 진 요청들끼리는 서로 기다리지 않고 병렬로 끝난다.
  그래서 N이 커져도 시간이 커넥션 풀 병렬도에 맞춰 늘어난다.
- complete가 **끝난 곡의 ID를 받도록** 바꿨다. 이게 3-1(순차 실행)까지 고치는 핵심이다. 같은
  요청이 두 번, 세 번 와도 결과가 같다(멱등성).

### 5-3. 해결책 ② 비관적 락: 먼저 잠그고 나서 판단

```sql
SELECT ... FROM queue_items WHERE id = :A FOR UPDATE   -- 락을 잡은 뒤에 status를 확인
```

- 판단을 락 **안에서** 하므로, 락을 잡았을 때는 항상 앞 요청이 커밋한 최신 상태를 본다.
  나머지 코드(dirty checking)는 현재 코드와 같다.
- 하지만 `FOR UPDATE`는 행의 상태와 상관없이 **모든 요청이 그 행 락을 한 번씩 독점**한다. 이미 끝난
  곡을 확인만 하고 돌아갈 요청도 줄을 서야 한다. 그래서 시간이 N에 정비례한다(요청당 약 1.1ms × N).
  N=500에서 ①보다 2.8배 느렸다.
- 락을 기다리는 동안에도 DB 커넥션을 붙잡고 있다. 커넥션 풀이 10개뿐이면, 한 곡에 요청이 몰렸을 때
  다른 매장이나 다른 API까지 커넥션을 기다리게 된다.
- N≤10에서 ②가 더 빨랐던 이유는 측정하지 않았다(가설). 이 구간은 줄이 짧아서 락 대기 비용이 작다.
  반면 지금 ① 구현은 요청당 SQL이 더 많다. `@Modifying`의 flush/clear, 진 스킵 요청이 날리는
  UPDATE 2번, 승격 후 재조회가 그렇다. 그래서 고정 비용이 먼저 보였을 가능성이 크다. SQL 로그로
  문장 수를 세면 확인할 수 있다.

### 5-4. 두 방식 모두 "ID를 받는 것"이 전제다

②도 순차 실행(3-1)에서 1곡만 넘어간 건 complete에 곡 ID를 줬기 때문이다. ID 없이 "지금 재생중인 곡"을
잠그는 방식이었다면, 락을 잡은 시점에는 이미 B가 PLAYING이다. 그래서 그대로 B를 끝내버린다.
**락은 상호배제(mutual exclusion)만 보장하고, 요청이 무엇을 대상으로 하는지는 보장하지 않는다.**
요청이 "무엇을" 바꾸려는지 명시해야 같은 요청이 두 번 처리되지 않는다(멱등성).

## 6. 최종 선택: ① 조건부 UPDATE

| 기준 | ① 조건부 UPDATE | ② 비관적 락 |
|---|---|---|
| 정합성 | 400/400 정상 | 400/400 정상 |
| 요청 몰릴 때(N≥100) | 빠름(2.4~2.8배) | N에 정비례해 느려짐 |
| 요청 적을 때(N≤10) | 약간 느림(절대값 10~25ms) | 빠름 |
| 락 보유 | 이긴 요청만 짧게 | 모든 요청이 한 번씩 독점 |
| 커넥션 점유 | 진 요청은 즉시 반환 | 락 대기 중에도 점유 |
| 데드락 위험 | 행 하나씩 순서대로 바꿔서 낮음 | 잠그는 행이 늘면 순서 관리 필요 |
| 코드 | JPQL `@Modifying` 쿼리, dirty checking 대신 반환값으로 분기 | 기존 구조 유지, 조회만 `@Lock`으로 교체 |
| 스키마 변경 | 없음 | 없음 |
| 서버 여러 대 | DB 문장 하나라 그대로 안전 | DB 락이라 그대로 안전 |

**선택 이유**

1. 실제로 몰리는 요청은 "같은 곡을 끝내라"는 중복 요청이다. TV의 ENDED 재전송, 관리자 연타,
   폴링 재시도가 그렇다. 진 요청은 할 일이 없다. ①은 이런 요청을 락 없이 0행으로 바로 돌려보낸다.
   ②는 할 일 없는 요청까지 줄을 세운다.
2. 요청이 적을 때 ②가 빠른 차이는 시행당 수 ms라서 사용자가 느낄 수 없다. 반면 몰릴 때 ②의
   손해는 커넥션 풀 고갈로 이어져 다른 API까지 번진다.
3. 문제의 진짜 원인은 "complete가 대상을 모른다"는 것이었다(3-1). ①은 그 원인을 "대상이 이 상태일
   때만 바꾼다"는 한 문장으로 직접 표현한다.

**적용 시 함께 바꿔야 할 것 (아직 운영 코드에는 적용하지 않음)**

- **API 변경**: `POST /now-playing/complete`가 끝난 곡의 `queueItemId`를 받아야 한다. TV는 이미
  `now-playing` 응답으로 `queueItemId`를 알고 있으니, ENDED 때 그 값을 보내면 된다. 2026-09-14에
  "서버가 지금 곡을 아니까 ID는 필요 없다"며 ID를 뺐는데, 이 실험으로 그 결정이 멱등성을 잃게 만든
  원인이었음을 확인했다.
- **폴백 곡**: 폴백은 `queue_items`가 아니라 `stores.current_fallback_video_id`로 상태를 관리한다.
  같은 원리로 `UPDATE stores ... WHERE id=? AND current_fallback_video_id = :끝난곡`이 필요하다.
  이번 실험 범위 밖이다.
- **남는 경쟁**: `addToQueue`의 "재생중인 곡이 없으면 바로 재생"도 같은 check-then-act 구조다.
  DB 차원에서 "매장당 PLAYING 1개"를 강제하려면 부분 유니크 인덱스(`... WHERE status='PLAYING'`)가
  필요하다. 마이그레이션이 필요한 변경이라 따로 결정해야 한다.
